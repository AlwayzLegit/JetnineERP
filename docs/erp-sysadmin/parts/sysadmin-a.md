### `SYS-001` Access ECL
*storis_ref: article 15234737969556*

**Purpose.** Drops the user into ECL command-line mode (the underlying Pick/D3 database shell). Escape hatch for STORIS support only — "You should not enter ECL command line mode unless directed by a STORIS representative."

**Where it lives.** `System Administration > System Tools > Access ECL`

**Fields**

| Field | Type | Purpose / business rule |
|---|---|---|
| (password prompt) | password | After the permission check passes, "the system then prompts for the log-on user's password." Re-authentication, not just permission. |

**Behavior & rules.**
- **Gated by the `Access ECL command line mode` field in the Extended Security settings.** This is a named permission flag; see `parts/user-security-CATALOG.md`. **Because Extended Security is a single global kill-switch (General System Control Settings), if Extended Security is OFF this permission is inert — meaning raw database shell access is not permission-gated at all.** That is the single most dangerous consequence of the kill-switch design we found in wave 1, and it is a concrete argument for our decision not to reproduce it.
- **Two-factor-ish pattern:** permission flag AND live password re-entry. Worth copying for destructive admin routines.
- Secondary containment: "You can also restrict access to this routine by removing it from the user menus" — i.e. menu removal is treated as a security control (security by menu hiding). We should not rely on that; menus are presentation, permissions are enforcement.

**Dependencies.** `SEC-*` Extended Security (`Access ECL command line mode`); General System Control Settings global Extended Security switch; `SYS-076` Set Up Menus (menu-based hiding, sibling part).

**Build notes.** We do **not** ship a database shell escape hatch in the ERP. If we need one for support, it must be: (a) a separate operator-console binary outside the web app, (b) permission-gated by a live-scope permission that cannot be globally disabled, (c) re-auth on every entry, (d) **every session written to `RPT-AUDIT`** with start/end timestamps and the commands run. STORIS logs none of this — there is no change-audit log. `[DECISION NEEDED]` Do we allow any raw SQL console in production at all, or force all support access through read replicas?

### `SYS-002` Access Time Clock
*storis_ref: article 15234738561044*

**Purpose.** Employee punch-in/punch-out against the STORIS time clock. Tracks log-in/log-out activity and feeds a time-clock report.

**Where it lives.** `System Administration > System Tools > Time Clock > Access Time Clock`

**Fields**

| Field | Type | Purpose / business rule |
|---|---|---|
| `User ID` | code + Search lookup | The employee ID clocking in/out. Search button lists valid codes. |
| `Password` | password | **Case-sensitive.** On success a message displays the time the system logged you in or out. |

**Behavior & rules.**
- The screen is a **toggle driven by current state**: "If you are currently logged in, the system asks for your password to log you out. If you are currently logged out, the system asks for your password to log you in." There is no explicit IN/OUT choice — state decides.
- **Hard cap: "Employees can log in and out a maximum of four times in a calendar day."** i.e. 4 punch pairs / 8 punches per calendar day. The article does not say what happens on the 5th attempt.
- **Missed-clock-out recovery, exact behavior.** On first access of a day, if the prior day was never clocked out, a message asks if you want to log out. **If you answer yes, the system does three writes:**
  1. "clocks out the prior day's clock record at midnight,"
  2. "clocks in the current day's record at midnight, and"
  3. "clocks out the current day at the current time."
  **This means a forgotten punch-out silently bills the employee for midnight→now on the current day** — the record is fabricated, not flagged.
- **If you answer no:** "the process clocks in a new record at the current time and leaves the previous day in an error state." So there is an explicit `error` state on a clock record.

**Dependencies.** `SYS-051` Override Time Clock Entry (sibling part) — supervisor edit of staff clock data, itself security-clearance gated. User file / employee master.

**Build notes.** Implement punches as an append-only event log (`punch_in` / `punch_out` with actor, timestamp, source, geo/IP), never as a mutable pair. **Do not reproduce the auto-fabricated midnight rows** — that is a wage-and-hour liability. Instead mark the open shift `UNRESOLVED` and require a manager to close it with an explicit reason, writing both the original and the correction to `RPT-AUDIT`. Keep the 4-punch-pair/day cap as a soft warning, not a hard block (California meal-break patterns routinely produce more). `[DECISION NEEDED]` Does LA Mattress run payroll off the ERP clock at all, or is time capture staying in the existing payroll system? If the latter, `SYS-002`/`SYS-051` are out of scope entirely.

### `SYS-003` Administer Phantom Processes
*storis_ref: article 15234735777428*

**Purpose.** The control panel for STORIS background workers ("phantoms"). Start, stop, suspend, resume, tune, and inspect the log of any background process. This is the job-runner admin console.

**Where it lives.** `System Administration > System Tools > Establish and Review Phantom Processes > Administer Phantom Processes`. Also reachable by double-clicking a row in the *Show All STORIS Phantoms* grid.

**Fields**

| Field | Type | Purpose / business rule |
|---|---|---|
| `Process` | code + Search (Read-Only Lookup Window) | Process ID of the phantom to start/stop. **If reached from Show All STORIS Phantoms, this is pre-filled, dimmed and read-only.** |
| `Type` | display only | One of three STORIS-assigned types (see below). |
| `Status` | display only | Current status of the phantom named in `Process`. |
| `Update Interval` | display only (seconds) | The status-update interval. |
| `Queue Count` | display only | "the number of transactions waiting to be processed" for the selected phantom. |
| `Queue Name` | display only | Internal name of the process affected by this phantom. |
| `Status` (2nd) | display only | Status of the file displayed at `Queue Name`. |
| `Process ID` | entry / double-click from grid | Selects a running instance in the grid to act on. |
| `Action` | enum + Add button | The operation to perform (see enum below). |

**Behavior & rules.**
- **Phantom `Type` enum — exact values and semantics:**
  - `Administered` — "perform processing and sleep for the time specified in the Sleep Interval field before waking up and processing again." (long-running poll loop)
  - `Multi-threaded` — "performs update and immediately shuts down." (one-shot, fan-out)
  - `Scheduled` — "performs update at the pre-scheduled time or interval and immediately shuts down." (cron)
  - **Type is assigned by STORIS and is not editable by the customer.**
- **`Action` enum — exact values:** `View Log` (opens Phantom Process Log window; exit via Clear or Exit) · `Tune Parameters` (opens Phantom Tuning Window, editable: **Sleep Time** and **Status Update Interval**) · `Stop Phantom` · `Display PH File` (raw phantom PH file dump).
- **Stopping a phantom does not delete its record:** "When you stop a phantom process, its phantom record remains on file so users can still view any log comments that exist for the phantom." Log retention survives process death.
- **Actions button (bottom of screen) — a separate set:** `Start New Phantom` ("Starts a new phantom (with its own Process ID) for the selected process" — **so a single process can have multiple concurrent workers**), `Suspend/Resume` (toggle; the Status field under Process reflects it), `Auto Start/Stop Mode` (toggle).
- **These three Actions are available for `Administered` type phantoms only, and require a selected grid line.** Scheduled and multi-threaded phantoms cannot be suspended or scaled from here.
- **Grid columns (exact):** `PID` (the UNIX process ID, unique per UNIX process), `Operator` (employee ID of the user who initiated the phantom), `Date` / `Time` (phantom start), `Sleep` (current sleep time), `Update` (current status update interval), `Status` (text of last status update), `Date` / `Time` (of last status update), `Count` (transaction count posted at last status update).
- **Operational hard rule, verbatim from the article:** "If you must shut down your server, STOP ALL PHANTOM PROCESSES RUNNING ON THE SYSTEM BEFORE SHUTTING DOWN." **STORIS phantoms are not crash-safe — an unclean stop is expected to corrupt or strand work.** This is the strongest signal in the section that background jobs are not transactional.

**Dependencies.** `SYS-052` Phantom Process Log, `SYS-053` Phantom Process Settings, `SYS-093` View Phantom Processes (all sibling part). Feeds/serves EOD and EOM (`SYS-030`/`SYS-031`) and the data-warehouse resync. Read-Only Lookup Window (shared control).

**Build notes.** This is the closest STORIS analogue to our job queue. Our version must be **crash-safe by construction** — durable queue, at-least-once delivery, idempotent handlers, visibility timeouts — so that "stop all workers before rebooting" is never advice we have to give. Keep the useful parts of this UI: per-queue depth, per-worker last-heartbeat, last status text, processed count, operator who started it, suspend/resume, and per-worker log. Add what STORIS lacks: retry counts, dead-letter queue, and failure alerting. Do not copy `Display PH File` (raw internals) or `Start New Phantom` as a manual step — worker count should be a configured concurrency number, not something an admin spawns by hand. Every start/stop/suspend should write to `RPT-AUDIT` (STORIS records only the starting operator, and only while the record lives).

### `SYS-004` AP and GL History Conversions
*storis_ref: article 15234718452500*

**Purpose.** One-time migration utility that converts historical Accounts Payable and/or General Ledger data from STORIS Revision 7.3-or-later into STORIS Accounting. Directly relevant to `MIG-*`.

**Where it lives.** Article gives no menu path (STORIS-personnel routine). **"STORIS personnel use this routine"** — it is not customer-runnable.

**Fields**

| Field | Type | Purpose / business rule |
|---|---|---|
| `Convert` | enum, select one | Options: `AP`, `GL`. **"If one or both of these options does not appear, the file has already been converted and thus is not available."** |
| `STORIS Accounting Path` | path | Path to the target AP/GL account. |
| `GL History Years to Convert` | integer | Number of years of historical data to bring over. |
| `Print Error Report` | checkbox | "To print an error report, check the box. Otherwise, leave the field blank." |
| `Send Output to` | display only | Output destination; changed via `Actions > Output Settings`. |
| `Export Path` | display only | For `Personal Report Viewer (PRV)`, `Excel Export`, or `ASCII Export` destinations, shows the pre-set drive/folder. **"You cannot edit the export path using this process."** |

**Behavior & rules.**
- **Hard prerequisite: "You must be running STORIS Accounting to use this process."**
- **Explicitly NOT idempotent — it is once-only by design.** The utility hides the `AP` / `GL` option once that file has been converted. That is the anti-rerun guard: state is tracked on the source file, not on the rows. Contrast with `SYS-005`/`SYS-035` (Import Data), which **is** re-runnable but **not** idempotent and will happily create duplicates.
- **`GL History Years to Convert` is a truncation knob** — history older than N years is silently not migrated. Nothing in the article says the operator is warned about what falls off.
- Error report is **opt-in** (unchecked = no error report). Bad default for a migration.

**Dependencies.** STORIS Accounting module. `MIG-*` cutover plan. Output Settings / print-destination framework shared with `SYS-007`.

**Build notes. (MIG)** For our cutover: (1) the "years to convert" truncation must be a **deliberate, documented decision with a reconciliation report of what was excluded**, not a silent cut — if we bring 3 years of GL we must be able to state the opening balance that carries the rest. (2) The once-only lockout is the right instinct but the wrong mechanism: our importer should be **idempotent on a natural key + source-batch id**, so a re-run is a no-op rather than being blocked. (3) Error reporting is **always on**, never a checkbox. (4) Trial-run/dry-run mode with full rejects listing before any write — STORIS has no dry run here. `[DECISION NEEDED]` How many years of AP/GL history does LA Mattress actually need live in the ERP versus archived read-only outside it?

### `SYS-005` AP Bill Conversion
*storis_ref: article 15234718455060*

**Purpose.** Spreadsheet-driven import of **customer refund** AP bills when upgrading from an earlier STORIS release. Run through the generic `Import Data` routine (`SYS-035`) using the `AP Bills - Customer Refunds` worksheet of the Conversion spreadsheet. Highly relevant to `MIG-*`.

**Where it lives.** Not a menu screen of its own — it is a *worksheet + procedure* executed via `Import Data`. Spreadsheet is downloaded from the STORIS secure customer-service web site (log in with the Customer Service web site User ID/Password, then Downloads page → Conversion Spreadsheet link).

**Fields** — the article documents the *procedure and required columns*, not a screen. Required per-row data:

| Field | Type | Purpose / business rule |
|---|---|---|
| vendor | code | Required. "For customer refunds, you normally use the RFND vendor." **Recommendation: create an alternate refund vendor, e.g. `RFND2`, so imported refunds are distinguishable from natively-entered refunds.** |
| customer | code | **Required — "The import program rejects refund AP bills with no customer."** Recommendation: create a dedicated placeholder customer for AP bills that have no real customer. |
| GL account | code | Optional on the sheet. **Fallback rule below.** |

**Behavior & rules.**
- **Scope limit, verbatim: "At this time, the only AP bill type supported by this spreadsheet is Customer Refund."** No other AP bill types can be imported by this route. This is exactly the kind of "what it cannot import" the cutover plan needs.
- On success "the system creates a customer refund AP bill and generates the appropriate GL hits" — **the import posts to the GL, it is not a data-only load.**
- File format: enter data in the worksheet, then **"save the file as a tab-delimited .txt file"** before running `Import Data`. Not .xlsx.
- **GL account fallback rule (hard):** the GL account for customer refunds is configured at `General Ledger Assigned Account Settings > Customer Refunds Payable` and may be named per-row on the sheet. **"if you do not specify a GL account for one or more bills on the spreadsheet, the system uses the Accounts Receivable GL account for those bills."** — a silent fallback to A/R, which is almost certainly not what you want. **This will mis-post quietly.**
- **Closed-period rule (hard, and asymmetric):** "AP bills cannot be imported into a closed period if this is run on a live account. **However, if this process is run on a learn account, STORIS does allow AP bills to be imported into a closed period.**" So the learn/training account deliberately relaxes period control — meaning **a learn-account rehearsal does not prove the live run will succeed.** Critical for cutover rehearsal planning.
- **GL source stamp:** every imported customer refund is stamped GL source `APIR` ("Accounts Payable Import - Refund"). Gives a clean handle for reversing/identifying the import.
- **Per-record outcome enum (exact three values), from the error report:**
  - `converted` — "the record was successfully added to the STORIS database."
  - `error` — "the record was not converted to the STORIS database, a brief explanation appears."
  - `warning` — **"the record was converted to the STORIS database, but with conditions. A brief explanation appears. Check the record in STORIS for integrity."** i.e. warnings are *written* rows that may be wrong. Rejects and warnings are different populations and both need review.
- **NOT IDEMPOTENT — the single most important line for `MIG-*`, verbatim:** "Important! If errors occur when you run the Import Data process to convert refund AP Bills, you can run the process again for the items that were rejected the first time. HOWEVER, you must edit the spreadsheet and remove any data that has already been accepted and loaded into STORIS. When re-running the process, your spreadsheet should only contain data that was rejected, and/or any new data. **Otherwise, duplicate AP Bills are created on the STORIS system and are not easily corrected.**" There is no dedupe key, no batch id, and no un-import.
- Reconciliation aid: "Each time you run the Import Data process using the AP Bills Conversion Spreadsheet, the program automatically generates the **Report Payables Activity** report, listing dollar totals for all refunds successfully converted." — a control total for tie-out.

**Dependencies.** `SYS-035` Import Data (the executing routine); `SYS-016` Create a Catalog Spreadsheet (same spreadsheet-download pattern); General Ledger Assigned Account Settings (`Customer Refunds Payable`); vendor master (`RFND`); customer master; accounting period control; `SYS-015` Copy Live Data to Learn Account (learn-account relationship); `MIG-*`.

**Build notes. (MIG — high value)** Our importer must fix all four defects here:
1. **Idempotency by construction.** Every import row carries a stable `source_key`; every run carries a `batch_id`. Re-running the same file is a no-op, not a duplicate. **Every imported record stores its `batch_id` so a whole batch can be reversed in one action** — STORIS has no un-import at all.
2. **No silent GL fallback.** A missing GL account is a *reject*, never a fallback to A/R. If we want a default it must be an explicit, named, per-import-type default the operator confirms up front.
3. **Same period rules in rehearsal as in production.** Do not build a sandbox that relaxes closed-period control — the whole point of a rehearsal is fidelity. If we want to load into closed periods for a cutover, that is a one-time, explicitly-flagged migration mode with its own approval, applied identically in rehearsal and live.
4. **Keep the good parts:** the three-state per-row outcome (`converted` / `error` / `warning`) is a good model and warning ≠ success is worth preserving loudly; the `APIR`-style source stamp per import type; and the automatic control-total report after every run.

`[DECISION NEEDED]` Do we migrate open customer refunds/AP at all, or settle them in the legacy system and start clean? The duplicate-risk profile here argues strongly for the latter.

### `SYS-006` Assign Conversion Import Translations
*storis_ref: article 15234721250196*

**Purpose.** A value-mapping table applied automatically during `Import External Data` — translates a source system's codes into STORIS codes before the write. Directly relevant to `MIG-*`.

**Where it lives.** `System Administration > System Tools > Conversion Tools > Assign Conversion Import Translations`

**Fields**

| Field | Type | Purpose / business rule |
|---|---|---|
| `Import Provider` | dropdown (Arrow) | Provider of the information to translate; chosen from the list of available import providers. |
| `Import Type` | dropdown (Arrow) | Import type to translate; from list of available import types. |
| `Element Name` | dropdown (Arrow) | The element/field to translate; from list of available element names. |
| `Original Value` | text | "Enter the text to be translated (e.g. EACH)." |
| `Translated Value` | text | "Enter the value you wish to have the original value translated to when writing to the STORIS database. (e.g. EA)." |

**Behavior & rules.**
- Rows are added to the grid with `Add`. Grid columns: `Original Value`, `Translated Value`.
- **The mapping key is the triple (`Import Provider`, `Import Type`, `Element Name`) — mappings are scoped per provider per import type per field, not global.** Good design; worth keeping.
- **"If you have established a translation value, the import process automatically performs the translation prior to updating the STORIS database."** Translation is silent and automatic — no per-row indication in the target that a value was rewritten.
- The article does **not** state what happens to an unmapped `Original Value` (pass through raw? reject?). Unspecified — must be decided by us.

**Dependencies.** `SYS-036` Import External Data (the consumer), `SYS-010` Automated Data Import Settings, `SYS-071` Select and Configure a Vendor for Import (sibling part), `SYS-034` Import Cross Reference Data. `MIG-*`.

**Build notes. (MIG)** Keep this concept — a per-(source, feed, field) value-translation table is exactly right for both cutover and ongoing vendor feeds, and it is the correct place to absorb "their UOM is EACH, ours is EA." Improvements over STORIS: (a) make the unmapped-value behavior an explicit per-element policy — `pass through` / `reject row` / `reject and report` — defaulting to **reject and report**, so we discover unmapped vendor codes instead of importing garbage; (b) **record on each imported row that a translation was applied and what the original value was**, so the rewrite is traceable; (c) surface an "unmapped values seen in the last N runs" report so the mapping table can be maintained proactively; (d) allow regex/prefix rules, not just exact-value pairs, or the table becomes unmaintainable at vendor-catalog scale.

### `SYS-007` Assign Daily Reports Print Destination
*storis_ref: article 15234722956820*

**Purpose.** Defines where each End-of-Day (EOD) report is delivered — by printer, by organizational level, or to STORIS Messenger users. The routing layer of the EOD job (`EOD-001`).

**Where it lives.** `System Administration > System Tools > Review Daily and Monthly Activity Summaries > Assign Daily Reports Print Destination`

**Fields**

| Field | Type | Purpose / business rule |
|---|---|---|
| (module grid) | grid | Lists available modules. **Double-clicking a module opens the `Cycle Module Multi-Print Assignment Screen` (`SYS-019`)**, which shows that module's EOD reports and their current print destinations. |

**Behavior & rules.**
- **Print destination levels (exact enum):** `Corporate`, `Regional` ("provided Regional Processing is active on your system"), `Store`.
- **"based on report criteria restrictions, the Regional and Store options are not available for all reports."** Some EOD reports are corporate-only by nature — destination level is a property of the report, not freely chosen.
- Destination editing and Messenger-user assignment happen on the child screen (`SYS-019`), not here. This screen is just the module picker.
- **Local Printer rules (hard, and surprising):** for users whose User file Output tab is set to `Local Printer`:
  - **"If Regional Processing is active on your system, printing is not available from the End-of-Day and End-of-Month processes."** — enabling Regional Processing silently kills local printing of EOD/EOM output.
  - EOD writes files to `C:\Documents and Settings\USERID\My Documents\STORIS\Reports\EOD_YYYYMMDD`
  - EOM writes files to `C:\Documents and Settings\USERID\My Documents\STORIS\Reports\EOM_YYYYMMDD`
  - **"If printing reports for an account other than the Live account (for example, the Learn account), the program appends the account name to the end of the folder name":** `...\Reports\EOM_YYYYMMDD_ACCOUNTNAME`. The Live account gets **no** suffix — so the absence of a suffix is what marks production output. Fragile.
  - Paths shown are Windows XP; "For Vista® and Windows 7® PCs, substitute 'Users' for 'Documents and Settings'."

**Dependencies.** `SYS-019` Cycle Module Multi-Print Assignment Screen (child editor); `SYS-008` Assign Monthly Reports Print Destination (EOM twin); `SYS-023` End of Day Reports; `SYS-030` Generate Daily Reports / `EOD-001`; Regional Processing system setting; User file → Output tab → `Local Printer`; STORIS Messenger.

### `SYS-010` Automated Data Import Settings
*storis_ref: article 15234721248788*

**Purpose.** Registers a set of recurring, file-based data imports so they run **unattended** — either as a step inside End-of-Day (`EOD-001`) or on a schedule via `Schedule a Process`. This is STORIS's ETL scheduler. **Directly relevant to both `EOD-001` and `MIG-*`.**

**Behavior & rules.**
- **EOD integration (this is a documented EOD step — feeds `EOD-001`):** "During EOD processing, the system checks for the presence of a data import file in the location specified on this screen. **If found, the data import is processed during EOD.**" So EOD is **file-presence-triggered**: no file, no import, no error.
- **Scheduled-process integration:** "at the scheduled interval (day/time) the system looks for the import file based on the name and location settings established on this screen. If an unprocessed file is found, the data import process is run."
- **Duplicate prevention is by file rename, verbatim: "To prevent duplication, processed files are renamed."** That is the entire idempotency story — a filesystem side-effect. **If the rename fails, or someone restores the original filename, the import re-runs and duplicates.** No batch id, no content hash, no processed-file ledger.
- **Concurrency guard:** "the system checks to make sure **no other product/district and regional product/kit master import phantoms are currently running**." Note this guard is described only for the product/kit family — nothing says customer or vendor imports are similarly guarded.
- **File format:** spreadsheets are supplied by STORIS in Excel format; **"save the file as a tab-delimited .txt file"** to a drive on the server or PC accessible to the user. One row per product/vendor, in the applicable worksheet (e.g. the `Vendor` tab).
- **Quantity-on-hand import semantics (hard rule):** "the import data process has the ability to remove inventory pieces that have been transferred back to the warehouse, as well as to add store inventory pieces that have been transferred from the distribution warehouse. **For negative QOH adjustments, you must include the negative sign (-) when entering the Quantity in the spreadsheet.**" **So the QOH import is a signed *delta/adjustment*, not an absolute set-to value.** Getting this wrong silently doubles or zeroes inventory. Critical for `MIG-*` and for any recurring stock feed.
- **Per-record outcome enum — same three values as `SYS-005`:** `converted`, `error`, `warning` ("the record was converted to the STORIS database, but with conditions… Check the record in STORIS for integrity"). The report calls these `E` type and `W` type.
- **Error report reprint path:** `Import Data` process → select the conversion file → `Actions > Error Report` → opens `Report Data Imported Errors and Warnings` (`SYS-063`, sibling part), where you pick the run by `Date` and `Time`. So run history *is* retained and re-reportable — the only run-history mechanism found in this half of the section.
- **Both error and warning inclusion are opt-in checkboxes.** It is possible to configure an unattended nightly import that reports nothing at all.

**Dependencies.** `EOD-001` / `SYS-030` Generate Daily Reports (host process); `Schedule a Process` (alternate host); `SYS-035` Import Data (manual equivalent + error-report reprint entry point); `SYS-036` Import External Data; `SYS-006` Assign Conversion Import Translations; `SYS-063` Report Data Imported Errors and Warnings (sibling part); `SYS-042` Maintain NFS Root Paths (NFS location resolution); `SYS-003` phantom framework (import phantoms + the concurrency guard); customer/product/vendor/kit masters; `MIG-*`.

**Build notes. (EOD + MIG — high value)**
- **This is a real, named EOD step: "process registered data imports if their file is present."** Record it for `EOD-001`. Its position in the EOD sequence matters — an inbound QOH or product import that lands *after* inventory valuation but *before* replenishment (`REPL-040`) would change what gets ordered. **The article does not state where in the EOD sequence it runs — see `SYS-030` for the authoritative step list.** `[DECISION NEEDED]` for us: our nightly import must run **before** any valuation/replenishment step and the ordering must be explicit, not emergent.
- **Replace rename-based dedupe with a processed-file ledger** keyed on (source, filename, content hash, size, mtime) plus a `batch_id` on every imported row. Re-presenting an already-processed file is detected and skipped with a clear message, not silently re-imported.
- **Make QOH import mode explicit per feed — `DELTA` vs `ABSOLUTE` — and require the operator to choose.** STORIS's sign-convention-only approach is a standing production incident waiting to happen.
- **Errors and warnings are always reported**; no opt-out checkboxes. Add: alerting when an expected file *does not* arrive (STORIS's "no file, no import, no message" is a silent-failure mode — a vendor feed can stop for weeks unnoticed).
- Keep `Revised On` (schema/template version from the file header) and **reject files whose template version is older than the current one** rather than importing them under a changed column layout.
- Keep the `Account` display but make it impossible to get wrong: environment banner + refuse to run production imports from a sandbox session.
- The `PC` vs `NFS` location distinction and the 30/100-character limits are legacy artifacts — our imports land in object storage or an inbox endpoint, no client filesystem paths.

*storis_ref: article 15234720878356*

**Purpose.** The Actions menu of the data-conversion screen — run a conversion, wipe a conversion file, reprint the error report, and (in one specific routine) wipe all Configurator data for a vendor. **Contains two irreversible-destruction operations.** Relevant to `MIG-*`.

| Option | Purpose / business rule |
|---|---|

| `Clear File Conversion` | **DESTRUCTIVE — clears existing data from the selected conversion file, and from related files.** |
| `Error Report` | Reprints the error report for a prior run. |
| `Clear Configurator for Vendor` | **DESTRUCTIVE — removes all Configurator data for a vendor.** Only via `Update Product Configuration Detail`. |

**Build notes. (MIG — high value)**

### `SYS-019` Cycle Module Multi-Print Assignment Screen
*storis_ref: article 15234722706068*

**Purpose.** The per-report editor behind `SYS-007`/`SYS-008`. Sets, for each EOD/EOM report in a module, which organizational levels it prints at, who is notified via Messenger, and whether it is suppressed entirely. **Contains one of the most important `EOD-001` facts in this half of the section.**

**Where it lives.** Opened by double-clicking a module in `Assign Daily Reports Print Destination` (`SYS-007`) or `Assign Monthly Reports Print Destination` (`SYS-008`).

**Fields**

| Field | Type | Purpose / business rule |
|---|---|---|
| `Report` | code | The report whose print destination you are editing. Double-click a grid row to load it. |
| `Description` | display only | Description of the selected report. |
| `Corporate Print` | checkbox + `Add` | Print at corporate level during cycle processes. **Checked ⇒ a `Y` appears in the grid's `Corporate` column.** `Action` button → `Staff Selection` screen to notify users a corporate version is available — **"only permitted if the user(s) have STORIS messenger enabled."** |
| `Region/District Print` | checkbox + `Add` | Print at district/region level. Checked ⇒ `Y` in the `District/Region` column. `Action` → `Messenger Staff Assignment` screen. **"active only if 1) Regional Processing is active on your system and 2) the Regional print option is available for the selected report."** |
| `Location Print` | checkbox + `Add` | Print at store level. Checked ⇒ `Y` in the `Store` column. `Action` → `Messenger Staff Assignment`. **"active only if the Store print option is available for the selected report."** |
| `Suppress Print` | checkbox | Prevents the report from printing. Active only when `Report` is populated. |

**Behavior & rules.**
- **Fan-out rule — one print job per destination, verbatim:** "For each report you select to print, the program creates a separate print job for each of the print destinations specified for the report. For example, if you check the box at each of the Corporate, District/Region, and Store 'Print' fields below, the program creates separate print jobs for the corporate level (all levels), **each district and region included in the daily/monthly report**, and **each store location included in the current daily/monthly report**." **So checking all three boxes on a report at a 30-store chain produces 1 + (regions) + 30 print jobs of that one report.** Volume risk is real and unbounded.
- **Un-checking is non-obvious, verbatim:** "To remove a check from any of the 'Print' fields below, **click on the field until it is blank**, then click on `Add`. The associated `Y` disappears from the grid." — the checkbox is tri-state-ish and needs repeated clicking.
- **`Suppress Print` mutual exclusion (hard):** **"This field cannot be used when any of the `Corporate Print`, `Region/District Print`, or `Location Print` check boxes are checked. If any are checked, a warning appears and this `Suppress Print` check box is unchecked until you uncheck the conflicting check boxes."**
- **★ THE KEY `EOD-001` FACT, verbatim: "Checking this box suppresses the printing of the report only. Updates performed during the Generate Daily Reports process and applicable reports continue whether or not this box is checked."**
  **This confirms that in STORIS, End-of-Day is not a reporting job that happens to update things — it is an UPDATE job with reports attached. The reports are cosmetic output of the underlying posting steps, and suppressing a report does not skip its step.** This is the single most important architectural fact for `EOD-001`, and it directly supports the Inventory pack's assumptions in `PO-104` (PO closed-date stamping) and `REPL-040` (automatic PO replenishment): those are *updates* driven by EOD, not side effects of printing a report. **Corollary: you cannot disable an EOD side effect by turning off its report.**
- If `Suppress Print` is unchecked, "the report is printed as part of `Generate Daily Reports`."
- **Grid columns (exact):** `Report`, `Description`, `Corporate`, `Region/District`, `Location`, `Suppress Print`.
- **"This routine is not available for SaaS users."** (consistent with `SYS-008`).
- Restates: "Based on report criteria restrictions, the Regional and Store options are not available for all reports."

**Dependencies.** `SYS-007`, `SYS-008` (parents); `SYS-030` Generate Daily Reports / `EOD-001`; `SYS-031` Generate Monthly Reports; `SYS-023` End of Day Reports; `SYS-024` End of Month Reports; Regional Processing setting; STORIS Messenger; `Staff Selection` / `Messenger Staff Assignment` screens; `PO-104`, `REPL-040`, `REPL-041` (Inventory pack).

**Build notes. (EOD — high value)**
- **Separate the two concerns STORIS conflated.** In our ERP, nightly *posting steps* are a job pipeline with their own enable/disable, ordering, dependencies, retries and audit; nightly *reports* are consumers of the resulting data. Suppressing a report must be obviously and structurally incapable of skipping a posting step — and, equally, disabling a posting step must be a deliberate, logged, permission-gated act, not a checkbox next to a print option.
- Keep per-report scope selection (corporate / region / store) and Messenger-style notification, but **deliver by reference** (one generated report, N notifications) instead of N regenerated print jobs. STORIS's fan-out is a printing-era design.
- Replace the "click until blank" checkbox with a normal control.
- `[DECISION NEEDED]` Which of the ~dozens of EOD reports does LA Mattress actually want delivered nightly versus available on demand? The right default is: **all posting steps run, no reports are pushed, everything is browsable** — with an opt-in subscription list.

### `SYS-026` End-Of-Month Module Detail Screen
*storis_ref: article 15234722727188*

**Purpose.** Per-report run control for month end — enable/disable individual EOM steps, set their run-time options, and **recover reports left in an `Incomplete` state**. This is EOM's restart/resume mechanism.

**Where it lives.** Double-click a grid item in the `End-Of-Month Active Module Inquiry Screen` (`SYS-025`).

**Fields**

| Field | Type | Purpose / business rule |
|---|---|---|
| `Report` | name / double-click from list | The module report. **Double-clicking opens a menu with `More` ("view and/or modify the run-time options you want to use when this report runs during month ending processing") and `Select` ("modify the run status to Yes (Ready) or No (Inactive)").** |
| `Description` | display only | Description of the selected report. |
| `Run` | checkbox + `Add` | **Checked + `Add` ⇒ status `Ready`, "the report runs as part of month-end processing". Blank + `Add` ⇒ status `Inactive`, "the report does not run as part of month-end processing".** |
| `Status` | display | One of `Ready` / `Inactive` / `Incomplete` (see below). |

**Behavior & rules.**
- Grid shows, per report: `description`, `run (Y/N)`, `status`.
- **`Status` enum — exact three values and semantics:**
  - **`Ready`** — "include the report in month-end processing."
  - **`Inactive`** — "do not include the report in month-end processing."
  - **`Incomplete`** — a report that did not finish. **Recovery procedure, verbatim: "to reset the report status to ready, single-click on the item in the grid which highlights the row, then right-click and select `More` from the menu. The report appears on the screen in read-only mode. Click on `Run`. The report resets, you return to the End-Of-Month Module Detail Screen, and the report status updates to ready."**
- **★ ARCHITECTURAL CONTRAST WITH EOD — important for `EOD-001`.** At month end, **individual steps genuinely can be switched off** (`Run` = blank ⇒ `Inactive` ⇒ the step does not run). At day end, per `SYS-019`, the only per-report control is `Suppress Print`, which **explicitly does not skip the update**. **So: EOM steps are skippable; EOD steps are not.** That asymmetry means the EOD job is effectively an all-or-nothing nightly posting run, which is why `EOD-001`'s step *order* (rather than step selection) is the thing that matters.
- **`Incomplete` is the state that makes EOM restartable.** A failed month-end does not have to be re-run in full: failed steps sit in `Incomplete` and are individually reset and re-run. **STORIS therefore has per-step failure state and manual resume at EOM — and (as far as this half of the section shows) nothing equivalent at EOD.** That gap is worth flagging to whoever writes up `SYS-030`.
- **Turning a step `Inactive` is a permanent setting, not a one-run skip** — nothing in the article suggests it resets after the close. **A step disabled once to get through a bad month end stays disabled every month thereafter, silently.**

**Dependencies.** `SYS-025` (parent); `SYS-031` Generate Monthly Reports; `SYS-024` End of Month Reports; `SYS-032` Generate Monthly Reports after Daily Reports; `SYS-068` Right-Click Menus (sibling part).

**Build notes. (EOD/EOM)** Keep and generalize the `Ready` / `Inactive` / `Incomplete` model — it is the right one — but fix three things:
1. **Apply it to the daily close too.** Our nightly pipeline gets the same per-step states, so a failed step is visible, individually re-runnable, and does not force a full re-run. Add `Running`, `Succeeded`, `Failed`, `Skipped` and keep per-step timings and row counts.
2. **Distinguish "skip this run" from "disable permanently."** A one-off skip must expire automatically and be recorded with a reason; a permanent disable requires a permission and shows up on the close dashboard every period until someone re-enables it.
3. **Re-running a step must be idempotent or explicitly guarded.** STORIS's `Incomplete` → `Run` reset says nothing about partial writes already made by the failed attempt; ours must either roll back on failure or be safe to re-apply.

Also: every enable/disable/reset here is a change to how the books close and belongs in `RPT-AUDIT`.

| `Process Start-Time` | time `HH:MM`, 24-hour | **"Enter the start time as HH:MM in 24-hour military time format (for example, 10:00 P.M. is 22:00)."** **Leave blank to begin immediately.** `Run` starts it (at the time, or now). |
| `Generate Monthly Reports` | option (grid) | **"To initiate Generate Monthly Reports to run automatically at the completion of end of day processing, select this option. This option is not active if the end of month cannot be currently run."** (→ `SYS-032`) |

**Behavior & rules — the operational contract**

*Scheduling and exclusivity*
- **"Because users must be logged off the system when this process is run, STORIS recommends using a start time of late in the evening or early morning when no one will be using the system."** EOD requires exclusive access.
- **"Do not access the system till the day-ending process completes."**
- **★ HARD RULE, verbatim: "NOTE: Important: DO NOT use midnight (12:00) as the starting time. Enter a start time either before or after midnight."** No explanation is given. Almost certainly a date-rollover ambiguity in the scheduler. **A genuinely surprising, undocumented-reason landmine.**
- After `Run`, the **`End-Of-Day Snooze Screen`** shows `Start Time` and `Current Time` and the message **"Enter any key to abort EOD process."** — **so during the pre-start wait, ANY keypress aborts the run.** An unattended terminal with a cat on the keyboard silently cancels the nightly close.
- Then the **`EOD Progress Listing`** screen shows each process being performed with status **`Processing`** or **`Completed`**, plus a percentage progress bar. On success: **"End of Day finished at HH:MM:SS."**
- Duration is unpredictable: "The length of time the process takes to run varies among systems depending on which modules are active and the amount of data being processed."

*Re-running, catch-up and recovery — directly relevant to `REPL-041`*
- **"You can run the routine multiple times in a single day. Regardless, the program processes all data entered since the last time you ran the process."** **So EOD is watermark-driven and safe to run repeatedly — it processes the delta since the last run, not a fixed window.** This is the single most reassuring idempotency statement in the whole section.
- **★ FAILURE RESUME (exact): "If for some reason this process does not successfully complete, an error message appears the next time you run the process. You have the option to resume at the leave-off point or abort."** **STORIS's EOD therefore DOES have a resume-from-leave-off-point mechanism** — which corrects the tentative gap noted under `SYS-026`. It is coarser than EOM's per-step `Incomplete` state (which is individually addressable), but a checkpoint exists.
- **Missed days — two supported strategies, verbatim:** "If you skip the Day-Ending process for one or more days, you can: **run separate Day-Ending sessions for each day missed and thus run separate reports each day, or run the Day-Ending process once using the current date. Reports include information for all days since the you last ran the Day-Ending process.**" **The second option collapses several business days into one — reports and any date-stamped side effects then carry the single as-of date.** This matters for `PO-104`: a PO closed on a skipped day gets the catch-up run's `As-of Date`, not its true date.
- **★ `As-of Date` OVERRIDES TODAY'S DATE FOR SPECIFIC POSTINGS (exact): "The `Charge Off` and `Import Customer Payment` processes use the EOD date chosen here rather than today's date for performing updates and transaction posting when these processes are run from `Generate Daily Reports`."** **Confirms that EOD steps post using the `As-of Date` as the transaction date. This is the mechanism that supports `PO-104` (PO closed-date stamping): the closed date will be the EOD `As-of Date`, not the wall-clock date.**
- **Cross-cycle handoff: "Locked customer records skipped during `Generate Monthly Reports` are processed at next `Generate Daily Reports`."** **So EOM silently skips locked (in-use) customer records and defers them to the next EOD.** A month-end that runs while someone has a customer record open produces a month-end that is *incomplete for those customers until the next day*. **Hard rule, and a real reconciliation trap.**

*Composition — what actually runs*
- **"Reports produced during Day-Ending processing vary according to the active modules on your system and the settings in the account control files."** The step list is assembled per site. (Full catalogue: `SYS-023`.)
- **"STORIS provides the option to run processes of your choice as part of the End-of-Day process. For more information, contact STORIS."** **Custom, site-specific steps can be injected into EOD — so the documented list is not exhaustive at any given site.** (See also `SYS-018` Custom Plug-In Process Maintenance.)
- **Registered data imports run inside EOD** when their file is present (`SYS-010`).
- The **`Charge Off`** and **`Import Customer Payment`** processes are explicitly named as EOD-hosted processes.
- `Generate Monthly Reports` can be chained to run immediately on EOD completion (`SYS-032`).

*Error data and retention — cross-check against the destructive-retention findings*
- **"Use the `Report Data Import Errors and Warnings` process, which is accessed via `Import Data`, to regenerate error reports. Error data is retained until it is purged via `Generate Monthly Reports` as per the retention period set in `Days Retail Import Errors` in `General System Control Settings`."**
  **★ Direct confirmation of the wave-1/wave-2 finding that retention fields drive deletion at EOM.** Named setting: **`Days Retail Import Errors`** (`CFG-*`, General System Control Settings). **The purge executor is `Generate Monthly Reports`, not a purge utility.** Cross-check: `SYS-024` #7 `Report Purged Gift Certificate/Cards` is the same pattern. **Confirms: EOM is a purge engine driven by retention settings, and blanking or shortening a retention field destroys history at the next month end.**
- From the FAQ: **`Days Retain Interface Queue`** (Miscellaneous tab of `General System Control Settings`) governs spooler/print-queue retention — **"These settings accept an entry of 0 to 999 days with a default of 30, queue records are retained for that number of days before being purged via `Schedule a Process`."** **Note `0` is an accepted value and means immediate purge.**

*Printing / environment restrictions*
- **★ Exact rule (note the Cloud carve-out): "If you are not a Cloud client, have Regional Processing active, and your printer is set to Local (via the `Document Destination` field in the `User Print Settings`), you cannot run the EOD process. However, if you are a Cloud client using Regional Processing and are set to print locally, you can run the EOD process."** **A print-destination setting can outright block the nightly close on non-Cloud systems.** This refines the blanket statement in `SYS-007`/`SYS-008`.
- Reports may be sent to a **"hold" file** to be viewed/printed the following morning, via the **`Review Print Jobs`** program.

**Dependencies.** `SYS-023` End of Day Reports (the catalogue); `SYS-019` (suppressing a report does not skip its update); `SYS-010` Automated Data Import Settings (imports run inside EOD); `SYS-031`/`SYS-032` Generate Monthly Reports (chaining, locked-record handoff, retention purges); `SYS-069` Run a System Backup, `SYS-063` Report Data Imported Errors and Warnings (sibling part); `SYS-035` Import Data; `SYS-018` Custom Plug-In Process Maintenance; `Review Print Jobs`; `User Print Settings > Document Destination`; Regional Processing; **General System Control Settings → `Days Retail Import Errors`, `Days Retain Interface Queue`** (`CFG-*`); `Schedule a Process`; `Charge Off`; `Import Customer Payment`. **Inventory pack: `PO-104`, `REPL-040`, `REPL-041`.**

**Reconciliation against the Inventory pack's three assumptions**

1. **`PO-104` — PO closed-date stamping. SUPPORTED.** EOD posts using the `As-of Date`, not the wall-clock date — stated explicitly for `Charge Off` and `Import Customer Payment`, and `As-of Date` is documented as the date "the system updates all data up to … and bases all reports on". **A PO closed by EOD will carry the run's `As-of Date`.** ⚠️ **Caveat the Inventory pack must absorb: on a catch-up run covering several missed days, every PO closed across those days receives the single `As-of Date` of the catch-up run.** Closed dates are therefore not reliably the true close date unless EOD is run daily, one day per run.
2. **`REPL-040` — automatic PO replenishment is an EOD step. CONFIRMED.** `SYS-023` lists **`Replenish Stock Inventory Based on Sales Rate` (`PO.400.PRE`)** as an EOD entry, and `SYS-019` establishes that EOD entries are update steps whose printing can be suppressed but whose updates always run. **Replenishment therefore runs every EOD and cannot be turned off by suppressing its report.** (Whether it can be disabled at all — e.g. by deactivating the PO module or a control setting — is not stated here; `SYS-023`'s "varies according to active modules and control settings" is the only lever mentioned.)
3. **`REPL-041` — replenishment runs after receipts, sales, transfers and PO closings settle. SUPPORTED, NOT PROVEN.** The `SYS-023` catalogue orders replenishment at position 30, after all sales/transfer (`TE`), receiving/adjustment (`IC`), costing (`CT`) and cash-application (`AR`/`FR`/`VR`) entries, and before payables and GL. The list is demonstrably not alphabetical and not cleanly module-grouped (`TE.332` out of block; `IC.310`/`IC.315` appearing twice), which is consistent with a process-flow order. **This article confirms the run is "a sequence of reports"/"processes being performed" shown in order on the `EOD Progress Listing`, but never states that the `SYS-023` listing order equals that sequence.** **Recommendation: treat `REPL-041` as correct — it is the only ordering consistent with the evidence and with double-entry sanity — but record it as an inference, and if certainty is needed, the `EOD Progress Listing` screen of a live system is the artifact that would settle it.**

**Build notes. (`EOD-001` — the specification)**

*What to keep from STORIS*
- **Watermark/delta semantics.** "Processes all data entered since the last time you ran the process" — our nightly close should be a delta over a durable watermark, safe to run more than once a day.
- **An explicit business `As-of Date` that governs posting dates**, distinct from wall-clock time. This is correct and important; keep it.
- **Resume-from-checkpoint after failure**, with an explicit operator choice to resume or abort.
- **A live progress view** listing each step with status and elapsed time.
- **Optional chaining into the monthly close** when the month is eligible.

*What to do differently*
- **★ Never conflate "report" with "posting step" (the `SYS-019` defect).** Two separate registries: a **posting pipeline** (ordered, dependency-declared, individually observable, individually re-runnable, permission-gated to disable) and a **report catalogue** (subscriptions and destinations, zero effect on posting).
- **Pin ordering by declared dependencies, not by list position.** `replenishment.depends_on = [sales_settlement, receipts, transfers, po_closings, costing]`; `gl_posting.depends_on = [...everything...]`. This makes `REPL-041` a machine-checked invariant rather than an inference from a documentation ordering.
- **No exclusive-access requirement.** Our close must run against a live system. Where a step needs a consistent read, use a snapshot/as-of query, not a system-wide lockout. This deletes the entire class of problems around "users must be logged off", the midnight-start rule, and the abort-on-any-keypress snooze screen.
- **★ Never skip locked records silently.** STORIS's "locked customer records skipped during EOM are processed at next EOD" is a correctness hole. Ours retries with backoff, and anything still unprocessed at the end of the run is **reported as an exception on the close summary**, never deferred silently.
- **★ Catch-up runs must preserve true dates.** If N days were missed, our close runs **N sequential daily closes**, each with its own business date, rather than collapsing them. Collapsing is the thing that corrupts `PO-104`. If a collapsed run is ever allowed, it must stamp each record with its true event date and only the *report* with the run date.
- **Purges do not belong in the close.** Retention-driven deletion moves out of EOM into a separate, scheduled, permissioned job with a dry-run count and an acknowledgement (see `SYS-024`, `SYS-026` build notes). **A blank or zero retention field must never silently mean "delete everything" — it must mean "unset", and destroying data must require an explicit, positive instruction.** This is our correction to `Days Retail Import Errors`, `Days Retain Interface Queue` (`0`–`999`, default `30`, where `0` = purge immediately) and the `Group Payments by = None` behavior in the Inventory pack.
- **Site-specific custom steps must be declared and visible** ("we run these 3 extra steps") rather than injected by the vendor and undocumented.
- **Backups are infrastructure, not an EOD checkbox** with a tape in a drive. Keep a pre-close consistency snapshot, automatic and verified.
- **Failure must page someone.** STORIS surfaces an EOD failure the *next time you run the process*, i.e. up to 24 hours later. Unacceptable.

*`[DECISION NEEDED]` items for LA Mattress*
- What is the business day boundary — a fixed cutoff (e.g. 02:00 local), or per-store closing time? Multi-timezone?
- Are catch-up closes ever permitted, and if so must they be per-day?
- Which posting steps may an administrator disable at all, and who approves that?
- Retention periods for import errors, print/interface queue, and every other retention-governed dataset — with a firm rule that these are reviewed, not defaulted.

### `SYS-031` Generate Monthly Reports  ★ THE END-OF-MONTH / PERIOD-CLOSE JOB
*storis_ref: article 15234737083796*

**Purpose.** **"Use this routine to run monthly reports and processes and to close the period."** The accounting period close: it runs the `SYS-024` report/step set, **purges files according to retention settings**, and closes the oldest open month. The EOD companion to `EOD-001`.

**Where it lives.** `System Administration > System Tools > Review Daily and Monthly Activity Summaries > Generate Monthly Reports`. Also: chained from `Generate Daily Reports > Actions` (`SYS-032`), and schedulable via `Schedule a Process`.

> The article body is duplicated verbatim (two identical revision blocks). No content differs between them.

**Fields / Actions**

| Field / Action | Type | Purpose / business rule |
|---|---|---|
| `Parameter Maintenance` (Actions) | sub-routine | "select a series of STORIS standard reports you want to run as part of your 'end-of-month' process. **The routine saves your settings so that the next time you access the routine, you can either run the same set of reports or modify your list and run those reports.**" Opens `SYS-025` → `SYS-026`. **Settings persist across months — see the `Inactive`-is-permanent warning in `SYS-026`.** |
| `Run` | button | Initiates the close. |
| (confirmation) | typed `YES`/`NO` | Only when run on the last day of the period — see below. |

**Behavior & rules**

*Period model and overlap — the central constraint*
- **★ "STORIS allows you to leave two months open at one time - one previous month and one current month. The system does not allow posting to a second 'current' month."**
- **"You must run the Month-Ending process to close the previous month, but you need not run it on the last day of the month. We recommend you run the Month-Ending process between the 5th and 15th day of the current month (that is, before you reach overlap condition), to allow time for approving AP invoices, etc."** (Per the FAQ appendix under `SYS-030`: **overlap condition begins on the 20th**, after which transaction entry starts erroring.)
- **"To alert users of this issue, use the `System Notifications` process accessed via `General System Control Settings`."** (`CFG-*`)
- **Run during period overlap:** a message like **"Closing Period 06. Ending Date of 06/30/15. OK Abort."** — `OK` to close that period, `Abort` to cancel.
- **★ Run on the last day of the period (hard, and a trap): "If you run this process on the last day of the period you can close the period and generate the monthly reports, but you cannot process in that account until the first day of the next fiscal period."** Typed confirmation: **"If you enter 'YES' in the box, the current period is closed and the monthly reports are generated. Enter NO if you do not wish to proceed."** **Closing on the last day freezes all processing in that account until the next fiscal period begins.**
- **Run prior to the last day of the period: refused outright — "the following error is displayed and no reports are generated. When you click OK, the screen returns to the menu."** So the eligible window is: **the last day of the period (with a freeze warning), or any day in the following month up to overlap.**
- **Scheduled runs close the oldest month still open:** "Running `Generate Monthly Reports` this way closes the oldest month still open."
- Pre-run warning banner example: **"WARNING Closing period 06 ending 06/30/15 on 07/16/15."**

*Blocking preconditions*
- **★ "You cannot close a month if open freight batches exist."** Hard blocker.
- **Pre-flight checks with messenger alerting, verbatim: "Checks are performed in order to ensure completion of required processing before this process is run; if any items that prevent this report from running are identified, the process stops and the errors are communicated via STORIS messenger to the messenger administrator defined in `"When an EOD Logistical Error Is Reported"` on the Messaging tab of `STORIS Messenger Control Settings`. At this point, `Generate Monthly Reports` can be manually run or another run can be scheduled."** **This is the only push-alerting-on-failure mechanism found anywhere in this half of the section — and note it is wired to a setting named for *EOD* logistical errors.**
- **★ Physical inventory ordering rule (hard, verbatim): "If you recently performed a full physical inventory, it is strongly recommended that you complete the physical inventory update (`Update Physical Inventory Results`) PRIOR to running this month ending process. If you do not complete the update first, the system does not allow you to back-date your EOM processing to the date you ran the `Freeze Inventory` and you are prevented from adding more products to the physical inventory count."** Two consequences of getting the order wrong: EOM cannot be back-dated to the freeze date, **and the physical count is locked against additions.**
- Print restriction: identical to EOD — **"If you are not a Cloud client, have Regional Processing active, and your printer is set to Local (via the `Document Destination` field in the `User Print Settings`), you cannot run the EOM process. However, if you are a Cloud client using Regional Processing and are set to print locally, you can run the EOM process."**

*Irreversibility*
- **★ "Once you close a month, you cannot: backdate uncompleted orders into the closed month. resolve cost exceptions for that month."** **Unresolved cost exceptions become permanently unresolvable at close.** That is a direct argument for making costing-exception clearance a hard pre-close gate rather than advice.

*Purging — cross-check against the destructive-retention findings*
- **★ "NOTE: The Month-Ending process may purge certain files automatically, based on your system settings. If you are unsure about which of your files are scheduled for purging, contact your STORIS representative before you run this process."**
  **This is the smoking gun. It confirms — in STORIS's own words — that (a) EOM destroys data as a side effect of settings, (b) the set of things it destroys is site-dependent, and (c) *the customer is not expected to be able to determine what will be destroyed*.** Combined with:
  - `SYS-030`: import error data "is purged via `Generate Monthly Reports` as per the retention period set in `Days Retail Import Errors` in `General System Control Settings`";
  - `SYS-024` #7: `Report Purged Gift Certificate/Cards` (`AR.301.PRE`) is an EOM report, so gift certificate/card purging is an EOM step;
  - the wave-1/wave-2 findings that **blank retention fields delete history at the next EOM** and that **`Group Payments by = None` purges cash receipt records at the next EOD**;
  …this establishes a consistent, confirmed picture: **retention-driven destruction in STORIS is a silent side effect of the periodic close, governed by settings screens far away from the close, with no pre-run manifest of what will be deleted.** **Nothing in this half of the section contradicts that; multiple articles independently confirm it.**

*Other behavior*
- **Locked-record retry policy (exact, and more specific than `SYS-030`'s statement): "Updates to locked customer records are attempted 3 times then are skipped. `Generate Monthly Reports` proceed to the next process. Skipped records are processed at next `Generate Daily Reports`."** **Three attempts, then silently deferred to the next day's EOD. A month-end close can therefore be arithmetically incomplete for an arbitrary set of customers, with the shortfall landing in the following month's daily run.**
- **Costing method coupling: "During `Parameter Maintenance`, `Generate Monthly Reports` uses the `Costing Method` chosen in `Report Value of Inventory`. This only occurs if `Use Generate Monthly Report Parameters for Costing` in `Costing Control Settings` is enabled."** **So a report's parameter can determine the costing method used by the close — but only if a control setting says so.** (`CFG-*`)
- **Output archival: "All reports generated by `Generate Monthly Reports` are created in archive report format and can be viewed in `Review Archived Reports`."** Alternatively, if month-ending reports are set to be saved, use `Review Print Jobs` (from the Printing menu) to "view, print, and **delete**" them.
- **★ Cloud retention warning, verbatim: "If your database(s) is hosted in the STORIS Multi-Tenancy Cloud Environment, it is imperative that you save and/or archive End of Month reports. Backups for each report are only saved for a maximum of 3 weeks."** **Month-end close artifacts — the ones auditors ask for — are discarded after 3 weeks in the hosted environment.**
- Runtime messages may include "un-posted batches, number of periods set for BTA, etc." — **"For most messages, the program offers the option to continue (`Ignore` or `OK`) or not continue (`Abort` or `Cancel`) processing."** **So an operator can `Ignore` warnings about un-posted batches and close the period anyway.**
- Progress bar shows percentage complete.

**Dependencies.** `SYS-024` End of Month Reports; `SYS-025`/`SYS-026` (Parameter Maintenance); `SYS-030` Generate Daily Reports (chaining + locked-record handoff); `SYS-032`; `Schedule a Process`; `Review Archived Reports`, `Review Print Jobs`; **`General System Control Settings` → `System Notifications`, `Days Retail Import Errors`** (`CFG-*`); **`STORIS Messenger Control Settings` → Messaging tab → `When an EOD Logistical Error Is Reported`** (`CFG-*`); **`Costing Control Settings` → `Use Generate Monthly Report Parameters for Costing`** (`CFG-*`); `Report Value of Inventory` (`IC.320.PRE`) `Costing Method`; `Update Physical Inventory Results`, `Freeze Inventory`; freight batches; accounting period/fiscal calendar; `User Print Settings > Document Destination`; Regional Processing.

**Build notes. (period close)**
- **Adopt the two-open-periods model deliberately, or reject it deliberately.** It is a real and defensible design (it gives AP time to land invoices), but the consequence — **transaction entry begins failing on the 20th if the prior month is unclosed** — must be surfaced as a countdown on the dashboard from day one of the month, not as a cryptic "Transaction date cannot be in a future period" error at the point of sale. `[DECISION NEEDED]` What is LA Mattress's close calendar and who owns it?
- **Pre-close gates must be gates, not advice.** Ours: unresolved costing exceptions, open freight batches, incomplete physical inventory updates, un-posted batches, and unreconciled cash all block the close, each with a drill-down to the offending records. **No `Ignore` button on a data-integrity warning.** STORIS makes cost exceptions permanently unresolvable after close while letting you `Ignore` the warning that would have prevented it — that combination must not survive into our build.
- **★ Purging must be lifted out of the close entirely.** Separate job, separate permission, dry-run manifest ("this will delete N rows of type X, oldest Y, per retention setting Z"), operator acknowledgement, full `RPT-AUDIT` record, and a soft-delete/tombstone window before physical deletion wherever the data has any audit or legal significance. **"Contact your STORIS representative to find out what will be deleted" is the exact failure mode we are building to eliminate.**
- **Close artifacts are permanent records.** Signed, immutable, addressable by (period, report), retained per a documented policy measured in years, not 3 weeks. Never deletable from a print-job screen.
- **Locked records must never be skipped.** Row-level locks in a modern database are milliseconds, not a 3-strikes-and-defer situation; if a record genuinely cannot be processed, the close reports it as a blocking exception.
- **Keep the pre-run warning banner** ("Closing period 06 ending 06/30/15 on 07/16/15") and the typed confirmation — but make the banner a full pre-close summary: period, what will post, what will be purged, what checks passed, and what is being overridden.
- Keep **failure alerting to a named administrator** — and fix the setting's name so it is not filed under EOD.
- The `Use Generate Monthly Report Parameters for Costing` coupling is the kind of hidden, setting-gated behavior change we should not reproduce: **costing method is a property of the accounting policy, resolved once, not inherited from a report's parameter screen.**

**Build notes. (inventory + MIG)** This is the best-specified interface in the section and its shape is worth keeping: **export a manifest → third party counts → import counts → review and correct → post.** Requirements for ours:
- **Never let a blank key through as a warning.** Missing product key = reject the row, full stop.
- **Do not silently dedupe duplicate labels.** Duplicate scans are a real signal (double-counted aisle, cloned label); report them as exceptions and let the count supervisor decide.

### `SYS-034` Import Cross Reference Data
*storis_ref: article 15234718456980*

**Purpose.** Loads **legacy-code → STORIS-code** translation tables so that a conversion can rewrite old identifiers to new ones as it imports. The key-remapping counterpart to `SYS-006`'s value-remapping. **Central to `MIG-*`.**

**Where it lives.** `System Administration > System Tools > Conversion Tools > Import Cross-Reference Data`

**Fields**

| Field | Type | Purpose / business rule |
|---|---|---|
| `Import File` | full path + name; `Action` → browse | **"The file must be a tab-delimited .txt file."** **"The .txt file name you indicate here cannot be more than 26 alpha-numeric characters, not including the extension (.txt)."** |
| `File Name` | enum (pick the cross-reference type) | See the exact list below. |
| `Clear Cross Reference` | checkbox | **"Check the box to clear the information within the cross-reference file prior to importing a new .txt file. If the setting is unchecked, the cross-reference file is imported and duplicate ID's are overwritten. The setting is unchecked by default."** |

**Behavior & rules.**
- **Spreadsheet contract (exact):** "The cross reference spreadsheet is **provided by you** and contains **the legacy data in column A and the translated data in column B. When imported, column B overwrites the information in column A.**"
- **Worked example, verbatim:** "legacy product `SOFA-123` has to be changed in STORIS to `SOFA-ABC`. `SOFA-123` is in column A of the spreadsheet while `SOFA-ABC` is in column B. During the import process, `SOFA-ABC` overwrites `SOFA-123` whenever found."
- **★ "NOTE: The data conversion is skipped if either column is left blank."** **A blank on either side silently skips the mapping — no error, no reject. A half-filled mapping row is invisible.** This is the failure mode that leaves legacy codes scattered through a converted database.
- **★ Composite-key rule for storage locations, verbatim: "When creating a Storage Location cross reference, include the warehouse number as part of the key, i.e `88*DOCK`. This allows data to be uploaded for multiple locations."** — `*` is the key separator; `88` is the warehouse.
- **★ `File Name` — the exact list of cross-referenceable entity types (18):** `Brand`, `CS Problem`, `Customer`, `FR Merchant`, `Payment Type`, `Product Group`, `Product`, `Purchase Order Type`, `Reason Code`, `Sales Discount`, `Salesperson`, `Staff`, `Status Code`, `Stor Locn`, `Terms`, `Vendor`, `Warehouse Location`. **This list is effectively the inventory of identifier domains that must be remapped in a STORIS cutover — a ready-made checklist for `MIG-*`.**
- **Merge semantics without `Clear Cross Reference`: "duplicate ID's are overwritten"** — last write wins, so successive files layer on top of each other. **With it checked, the entire cross-reference file for that type is wiped first — a destructive option defaulted off.**
- "If your records are rejected or updated, a message indicates to view the conversion error report in `Report Data Imported Errors and Warnings`."
- "For further information on which conversions can process cross references, please see `Import Data Additional Information`." — **not every import honors cross-references; the set is documented elsewhere.**

**Dependencies.** `SYS-035` Import Data; `SYS-006` Assign Conversion Import Translations (value translation, vs this key translation); `SYS-063` Report Data Imported Errors and Warnings (sibling part); `Import Data Additional Information`; all 18 listed masters; `MIG-*`.

**Build notes. (MIG — high value)**
- **Use the 18-entity list as the cutover's identifier-remapping checklist.** For each: decide whether LA Mattress keeps legacy codes, adopts new ones, or maps; and record that decision. Codes that survive the cutover unmapped are the ones that cause "why does this product have two SKUs" tickets a year later.
- **Never skip a half-blank mapping row silently.** Blank on either side = reject with a message. This one line is the difference between a clean conversion and a long tail of orphaned codes.
- **Keep both the legacy and the new identifier on every migrated record** (`legacy_system`, `legacy_id`), permanently. STORIS overwrites A with B and keeps only the mapping file; we should be able to answer "what was this in the old system?" from the record itself, forever. That also makes reconciliation against legacy reports possible.
- **Make mappings versioned and additive**, with an explicit destructive "replace all" that names how many mappings it will delete. `Clear Cross Reference` defaulting to off is correct; keep that polarity.
- Adopt the composite-key idea (`warehouse*location`) but express it as real composite keys (tuple), not a delimiter convention — `*` in a legacy code would break it.
- Drop the 26-character filename limit and the tab-delimited-.txt requirement; accept CSV/XLSX with a declared header row (and **require** headers, unlike `SYS-033`'s "do not enter any column headings").

*Security*
- **"The ability to utilize any of these import processes depends on your security settings in `Create a User/Group Actions - Import Data Security`. *The Live-account gate — the most interesting control in this article*
- **`Authorized to Run Live` is customer-visible but STORIS-editable only ("LOCKED - STORIS access ONLY!").** Checked ⇒ that conversion file may be run in Live; unchecked ⇒ **"you cannot run this process in your Live account without STORIS intervention. *Other*
- **Re-run caution: "If you have already loaded your initial data, check with STORIS before running this process again."**
- **"Important! Consult with your STORIS representative before running this routine. Running this routine improperly can damage your data files. If you are already LIVE on the STORIS system, check with STORIS before running any data conversions in your LIVE account."**
- **Duplicate-email check on customer import (settings-gated), verbatim: "The following applies if the `Customer Entry - Warn if Primary Email exists for other Customers` setting is checked in the Customer page of `Point of Sale Control Settings`: If an email address is added or changed, the new email address is checked to determine if it has been assigned to any other customer account as a primary email address. **Build notes. (`MIG-*` — the specification for our importer)**

*What STORIS gets right and we should keep*
- **Per-entity, per-environment authorization to run.** The idea that "you may load Products in production but not Quantity on Hand or Invoice History without an extra approval" is genuinely good. Ours: an import-permission matrix of (entity × environment × role), with the highest-risk loads requiring a second approver. **We control it ourselves rather than having a vendor hold the key.**
- **Destructive clear blocked in production, structurally.**
- **Collision detection producing a `Record Already Exists` warning** rather than a duplicate.
- **A dedicated security domain for imports** with an explicit override path (audited).
- **Header/detail loads treated as one unit.**

*What we must do differently*
- **A dry run must not write** (see `SYS-014`). Our `Sample Amount` equivalent validates in a rolled-back transaction, so `Record Already Exists` never appears as expected noise and always means a real problem.
- **Every import is idempotent on a natural key + `batch_id`, and every batch is reversible.** No import in our system should behave like `SYS-005`.
- **Cascading clears enumerate what they will delete, by table and count, before confirmation.**
- **Duplicate-customer-by-email should be a merge candidate, not a dismissible warning.** Route to a dedupe review queue.
- **Ordering must be enforced.** STORIS says "convert file-by-file (for example, Vendor file, then Product file)" and leaves the order to procedure. Ours declares dependencies (`vendor` before `product`, `product` before `qoh`, `customer` before `order`, `order` before `invoice`) and refuses out-of-order loads.
- Drop the tab-delimited-.txt / 26-character-filename / per-PC-path constraints.

*`[DECISION NEEDED]` for the cutover plan*
- **Which of the header/detail document entities do we actually migrate?** `Order` (open orders — yes, mandatory), `Purchase Order` (open POs — yes), `Invoice`/`Invoice History` (history — how many years?), `Service Order History` (how many years?), `Revolving Receivables` (only if in-house finance exists).
- **Quantity on Hand is the highest-risk load** (signed-delta semantics per `SYS-010`, and STORIS blocks it by default for new Server clients). Recommend: **do not import QOH at all — establish opening stock from a full physical count taken at cutover**, which also gives a clean audited starting position.
- How much history goes into the ERP vs a read-only archive?

**Dependencies.** `SYS-033` Import / Export Physical Inventory Count (parent); `SYS-054` Physical Inventory Count Review (sibling part); `Report Physical Inventory Count Review`; `Update Physical Inventory Results`; `SYS-031` (physical inventory must be updated before EOM).

**Build notes.** Keep the review-before-commit gate and the `Errors Only` filter, and add what is missing:
- **Errors block the commit.** A count with unresolved errors cannot be posted; it can be saved as a draft, but the posting step requires zero errors or an explicitly recorded, per-row supervisor override with a reason. **This is inventory — the numbers become the balance sheet.**
- **Show variance before commit**, not just upload counts: counted vs book quantity and extended cost variance, by location and by product, with the largest variances first. That is what actually catches a mis-scanned aisle.
- **Correct in place** as well as re-import — forcing a round trip back to the spreadsheet for one bad row guarantees people will save-with-errors instead.
- Preserve the upload as an immutable artifact alongside the corrected result, so the count is auditable.

- Contract = (customer, plan, principal, misc, interest, insurance, terms, standard payment, balloon, written/activated/first-due/same-as-cash dates), with a derived amortization schedule and a derived balance.
- **`Same as Cash` (interest fully rebated if paid by date X) is a real and important promotional-finance construct** — "12 months same as cash" is standard in furniture/mattress retail. Model it explicitly, with the rebate computed at payoff.
- Fix STORIS's defects: **validate that the payment stream reconciles to the financed total**; **derive `Interest`/`APR` from each other and reject inconsistency** rather than storing an unused display rate on a consumer credit contract; make `Balloon` genuinely optional (zero allowed).

Silent disagreement with the legacy aging is how collections reports stop matching.

### `SYS-040` Load Import Tariff
*storis_ref: article 15234721552788*

**Purpose.** Imports US HTS (Harmonized Tariff Schedule) codes and duty rates from a government-published file, for linking to products and vendors — landed-cost support for imported merchandise.

**Where it lives.** `System Administration > System Tools > Conversion Tools > Load Import Tariff`

**Fields**

| Field | Type | Purpose / business rule |
|---|---|---|
| `Input Path` | display | Path of the file named in `Filename`. |
| `Filename` | filename + path; `Actions` → Windows browse | The tariff `.txt` file to import. |
| `Starting Range` | tariff number | First tariff to include in the import range. |
| `Ending Range` | tariff number | Last tariff to include. |

**Behavior & rules.**
- Source: **"First, you must download a list of tariffs onto your PC in the form of a .txt file"** — the article names the US International Trade Commission government site as the source. Manual, external download.
- **★ Two file layouts, both pipe-delimited — "including a delimiter in the form of the (|) ASCII character 124":**
  - **Full list:** `HTS No.|Stat Suffix||Level|Description|Unit of Quantity|Col. 1 Rate|Special Rate|Col. 2 Rate|Footnote / Comment` **(note the doubled `||` after `Stat Suffix` — an empty column in the full-list format)**
  - **Update list:** `0|HTS No.|Stat Suffix|Level|Description|Unit of Quantity|Col. 1 Rate|Special Rate|Col. 2 Rate|Footnote / Comment` — **"has an additional column at the beginning"**, a literal `0`.
  **The two layouts differ by more than the leading column: the full list has an extra empty field mid-record. A parser keyed only on "does it start with 0" would misalign.**
- **★ Rate selection rule, verbatim: "When building and/or updating records in the Tariff File, the system uses the 'Col. 1 Rate' field as the tariff's percentage."** **`Special Rate` and `Col. 2 Rate` are imported but not used as the tariff percentage.** (In HTS terms, Column 1 is the general/NTR rate; Special is preferential/FTA; Column 2 is the non-NTR rate. **So STORIS always applies the general rate and never the preferential one — which will overstate duty for goods qualifying under a trade agreement.**)
- **Effective dating: "The program defaults an effective date equaling the date on which you loaded new data and/or changed data. You can override this default."** — tariffs are effective-dated, and the default is load date (not the tariff's own statutory effective date). **Overridable, and should be overridden.**
- **Post-run report: "if any records were added or updated, a report displays listing the affected records as well as a list of products associated with the affected tariff codes."** **Impact reporting — it tells you which products are affected by the rate changes. Genuinely good, and rare in this section.**
- Imported tariffs are then viewed/edited in `Tariff Settings` and linked to products or vendors.

**Dependencies.** `Tariff Settings`; product master and vendor master (tariff linkage); costing / landed cost; `MIG-*`.

**Build notes.** Timely and relevant: **if LA Mattress imports mattresses or components, duty rates move and matter.** Requirements:
- **Fetch the schedule programmatically** on a schedule rather than requiring a manual download, and record the source revision.
- **Support `Special Rate` / preferential treatment**, keyed by country of origin and trade program. Applying Column 1 to goods that qualify for an FTA rate overstates landed cost and distorts margin and retail pricing. **This is a concrete improvement over STORIS, not a nicety.**
- **Effective-date from the statutory date, not the load date**, and keep full rate history so a landed cost can be recomputed as of any date.
- **Keep the impact report** — "these products are affected by these rate changes" — and extend it to show the cost/margin delta per product.
- Parse both layouts by field count and header detection, not by leading character; the `||` quirk above is exactly the kind of thing that silently shifts `Description` into `Level`.
- `[DECISION NEEDED]` Does LA Mattress import directly (own the customs entry) or buy landed from domestic distributors? If the latter, tariffs are the vendor's problem and this whole area is out of scope.

|---|---|---|

**Behavior & rules.**
- **★ THE HARD FINDING: a third-party routing application can write customer and delivery addresses back into the ERP.** Address changes made by a dispatcher inside RouteView flow back over a file path into the customer master. **No validation, approval, audit, or conflict-resolution behavior is described.** Given that STORIS has no general change-audit log (only `SAR-024`), **a customer's address can be silently changed by an external system with no trace of who changed it or why.**
- Round trip otherwise identical to `SYS-044`: STORIS → order/customer data for delivery-type sales orders → RouteView → manifest → STORIS.
- **"To use RouteView®, you must first install it on your system."**
- **Three separate routing integrations exist in this section** — ArcLogistics (`SYS-044`), RouteView (`SYS-047`), UPS Roadnet (`SYS-048`, sibling part) — all file-path based, all with essentially the same contract. Nothing describes how a site chooses between them or whether more than one can be active.

**Dependencies.** RouteView installation; sales order type (delivery); **customer master and delivery-address data (written by the external system)**; `SYS-044` ArcLogistics, `SYS-048` UPS Roadnet (sibling part); `SYS-020` Micro*D path; delivery scheduling; `RPT-AUDIT` (this is a prime candidate feed).

**Build notes — consolidated for the whole PC-path / integration family (`SYS-020`, `SYS-042`, `SYS-044`–`SYS-048`).**
- **One integration registry, not six screens.** Per integration: enabled flag, direction(s), endpoint/credentials, data mapping, schedule, retry policy, owner, and a **connection test**. Menu duplication (up to five paths to one setting in `SYS-020`) disappears.
- **Replace file drops with APIs.** Routing vendors all offer HTTP APIs now; a shared folder gives no delivery confirmation, no error signal, and no ordering guarantee. Where a file exchange is unavoidable, wrap it in the outbox/inbox pattern described under `SYS-028`/`SYS-029`: durable queue, per-record state, retries, dead-letter, and reconciliation.
- **★ Inbound writes from third parties must be gated and audited.** The RouteView address-writeback is the clearest example of what we must not reproduce. Our rule: **an external system may propose a change to master data; it may not commit one.** Proposed address changes land in a review queue (or are auto-applied only under a narrow, explicitly configured policy such as USPS-standardization-only), and **every applied change writes actor = the integration, timestamp, before/after values to `RPT-AUDIT`.**
- **Pick one routing provider** rather than carrying three half-integrations. `[DECISION NEEDED]` What does LA Mattress use for delivery routing today, and is routing in scope for the ERP build or staying as a separate system fed by an API?
- **No per-workstation paths anywhere.** Every integration artifact is server-side, addressable, retained per policy, and visible to support without remoting into someone's PC.

## Cross-cutting findings — reconciliation against the established requirements

### `EOD-001` — the end-of-day job. What we now know.

The three Inventory-pack assumptions, restated with verdicts (full argument under `SYS-030`):

| ID | Assumption | Verdict | Basis |
|---|---|---|---|
| `PO-104` | EOD stamps PO closed dates | **SUPPORTED, with a caveat** | `SYS-030`: EOD posts using the operator-entered `As-of Date`, not wall-clock ("The `Charge Off` and `Import Customer Payment` processes use the EOD date chosen here rather than today's date"). **Caveat: a catch-up run covering several missed days stamps them all with one date.** |
| `REPL-040` | Automatic PO replenishment is an EOD step | **CONFIRMED** | `SYS-023` lists `Replenish Stock Inventory Based on Sales Rate` (`PO.400.PRE`) as an EOD entry; `SYS-019` establishes EOD entries are update steps whose printing can be suppressed but whose updates always run. |
| `REPL-041` | Replenishment runs after receipts/sales/transfers/PO closings settle | **SUPPORTED, NOT PROVEN** | `SYS-023` places `PO.400.PRE` at position 30, after all `TE`/`IC`/`CT`/`AR`/`FR`/`VR` entries and before `AP`/`GL`. The list is neither alphabetical nor module-grouped, consistent with process-flow order — but no article states that listing order equals execution order. |

**The architectural fact that matters most (`SYS-019`, verbatim):** *"Checking this box suppresses the printing of the report only. Updates performed during the Generate Daily Reports process and applicable reports continue whether or not this box is checked."* — **EOD is an update job with reports attached, not a reporting job. You cannot disable an EOD side effect by turning off its report.**

**Other EOD/EOM mechanics established here:**
- EOD is **delta/watermark driven** and re-runnable: "the program processes all data entered since the last time you ran the process."
- EOD has **failure resume**: "You have the option to resume at the leave-off point or abort." EOM has finer-grained per-step `Ready`/`Inactive`/`Incomplete` state (`SYS-026`).
- **EOM steps can be switched off; EOD steps cannot.**
- **Registered data imports run inside EOD** when their file is present (`SYS-010`), triggered by file presence — no file, no import, no message.
- **Site-specific custom steps can be injected into EOD** ("STORIS provides the option to run processes of your choice as part of the End-of-Day process").
- **Mass Collector Reassignment runs as part of the customer cycle process** (`SYS-043`) — another cycle step.
- **EOM defers locked customer records to the next EOD** after 3 attempts (`SYS-031`), so a month-end can be arithmetically incomplete.
- **Two accounting periods open at most; overlap condition begins on the 20th, after which transaction entry starts failing** (FAQ appendix under `SYS-030`).
- **Closing a month is irreversible**: no backdating uncompleted orders into it, and **cost exceptions for that month become permanently unresolvable** (`SYS-031`).
- **`Even if Daily Backup Fails`** (`SYS-032`) lets an irreversible period close proceed with no verified backup.
- **Hard scheduling landmines:** do not start EOD at midnight (`SYS-030`); any keypress on the snooze screen aborts the run; a `Local Printer` setting plus Regional Processing blocks EOD/EOM entirely on non-Cloud systems.

### Purge / retention — cross-check verdict

**Confirmed, from three independent articles in this part, and nothing contradicts it:**
- `SYS-031`: **"The Month-Ending process may purge certain files automatically, based on your system settings. If you are unsure about which of your files are scheduled for purging, contact your STORIS representative before you run this process."**
- `SYS-030`: import error data "is purged via `Generate Monthly Reports` as per the retention period set in **`Days Retail Import Errors`** in `General System Control Settings`."
- `SYS-024` #7: **`Report Purged Gift Certificate/Cards` (`AR.301.PRE`)** is an EOM report — the purge is an EOM step.
- FAQ appendix: **`Days Retain Interface Queue`** (Miscellaneous tab, General System Control Settings), **`0`–`999`, default `30`**, purged via `Schedule a Process`. **`0` is accepted and means purge immediately.**

**Verdict: the wave-1/wave-2 finding is correct and now has direct textual support. Retention-driven destruction in STORIS is a silent side effect of the periodic close, governed by settings screens far away from the close, with no pre-run manifest of what will be destroyed — and STORIS explicitly tells the customer they cannot determine what will be deleted without calling the vendor.**

**None of the five flagged purge utilities fall in positions 1–47** — four are in the sibling half (56–60); `Purge Cash Drawer Data` does not appear in this section at all.

### Extended Security kill-switch — what this part adds

- `SYS-001` **Access ECL** is gated by the `Access ECL command line mode` flag in Extended Security. **Therefore, with Extended Security off, raw database-shell access is not permission-gated at all.** This is the sharpest concrete consequence of the kill-switch design found so far.
- `SYS-021` **Dynamic Escape Settings** names another exact flag: `Add programs to a Dynamic Escape screen listing` in `Create a User/Group Actions - System Security`.
- `SYS-035` **Import Data** names a distinct security domain: `Create a User/Group Actions - Import Data Security`, with a **security override screen** rather than a refusal.
- `SYS-009` **Assign Screen Action Permission` is a THIRD permission surface, keyed to the **user group live** (not copy-down). **STORIS therefore runs at least two inconsistent permission models side by side: group-live for screen actions, user-row copy-down for everything else.** A group change here takes effect immediately; a group change in the main model does not. Our single live most-specific-scope-wins resolver eliminates this.
- No article in positions 1–47 documents administering the Extended Security master switch itself.

### Contradictions and inconsistencies found within STORIS itself

4. **Two conflicting filters on one screen in `SYS-029`:** the automatic selection excludes previously-exported POs; the `Search` picker on the same screen includes them.
5. **Two permission models** (see above).
